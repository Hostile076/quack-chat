# 安卓端可行性评估：加一个 App，共用同一套数据

日期：2026-11-20　范围：`quack-chat` 现有代码（JavaFX 客户端 + Spring Boot 服务端 + SQLite）

---

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 加一个安卓 App 难不难？ | **中等偏难（3.5/5）**。不难在"数据"，难在"再写一遍 1.4 万行的客户端 + 手机端的长连接存活"。 |
| "使用同一套数据库，数据互通"要做多少事？ | **基本为零（1/5）**。现有架构已经是"服务端唯一数据源 + 多设备模型"，安卓端只要说同一套 WebSocket 协议，数据天然互通。 |
| 能不能让 App 直接连服务端那个 `quack.db`？ | **不能，这条路是错的**（见第 2 节）。 |
| 单人全职工期 | 聊天核心可用 **2–3 周**；MVP（登录/私聊/群聊/历史/未读/图片）**3 周**；对齐桌面全部功能 **10–14 周**。 |
| 最低成本的替代方案 | Web 版 + 套壳（PWA/TWA），**3–5 周**，代价是通话/通知/文件体验打折。 |

一句话：**这个项目已经为了"多端"设计过了，缺的不是数据库改造，缺的是第二个客户端。**

## 1. 现状盘点（评估的依据）

### 1.1 代码体量（真实行数）

| 模块 | 行数 | 说明 |
|---|---|---|
| `chat-common` | 1,256 | 协议信封 + 109 个命令字 + 67 个 DTO + 16 个 model，**纯 Java，零 UI** |
| `chat-server` | 6,521 | Spring Boot：WS 接入、命令分发、业务、内存态 + SQLite 落库 |
| `chat-client` | **13,995** | 其中 UI **9,645**、本地库 1,487、`AppContext` **1,799**、**网络层只有 322** |

关键比例：**网络层 322 行 / 客户端 14,000 行 = 2.3%**。
也就是说，"能连上服务器并收发消息"这件事只占桌面客户端的 2%；剩下 98% 是界面、状态编排、弹窗、媒体和窗口系统。**安卓端的工作量结构完全一样。**

### 1.2 服务端已经是"多端服务器"

- `SessionManager` 的路由表是 `userId -> deviceId -> ChatSession`（`ws/SessionManager.java`），**同账号多设备同时在线**是既有能力，`feature-checklist.md` 里有 E2E 用例（"同账号多设备同时在线 ✅"、"同设备重复登录踢掉旧连接 4001 ✅"）。
- 每台设备在每个会话有独立离线游标（`store/OfflineCursorStore.java`），登录时按游标补发（`LoginHandler.catchUp`，每会话上限 100 条）。
- `PushService.deliver()` 对目标用户的**所有设备扇出**，只跳过"产生这次动作的那台设备"——所以手机上发的消息，桌面端会实时收到。
- 未读、已读位点、好友备注、资料、动态编辑都有多端同步推送（`unread.push` / `msg.read.push` / `friend.remark.push` / `friend.updated` / `moment.edited.push`）。
- 桌面端的 `deviceId` 是**每次安装随机生成的 UUID**（`store/AccountStore.java:66`），不存在"电脑占了默认设备位"的问题——手机用自己的 deviceId 即可，互不干扰。

### 1.3 数据与媒体

| 项目 | 现状 |
|---|---|
| 权威数据 | 服务端内存态 + `data/quack.db`（SQLite，**16 张表**，WAL 模式），由 `store/PersistenceService.java`（52KB）落库 |
| `sql/schema.sql` | 是 **MySQL 版 V2 设计稿**，不是运行库；运行库表结构在 `PersistenceService` 里（accounts / profiles / friendships / messages / read_state / offline_cursor / unread_state / moment_state …） |
| 消息模型 | `ChatMessage{id, clientMsgId, from, fromName, to, chatType, msgType, content, ts, fromAvatar, seq, edited}`，会话内 `seq` 是排序/同步/已读的唯一依据 |
| 传输 | WebSocket 文本帧 + JSON 信封，`ws://host:8080/ws`，单帧 64KB，心跳 25s / idle 120s |
| 文件 | HTTP：`POST /api/upload`（multipart，**300MB 流式**）+ `GET /api/files/{id}?exp&sig`（HMAC 签名、支持 Range 206）。返回的 `url` 是**相对路径**，客户端自己拼 base——对手机友好 |
| 鉴权 | WS 用 `login` 命令（账号+密码）；HTTP 用 Bearer token（`AuthService`，**内存态、7 天、重启即失效**） |
| TLS | 已有 `application-tls.yml` profile（8443，PKCS12），但默认跑明文 8080 |

## 2. "同一套数据库"的三种理解，只有一种成立

| # | 理解 | 成立？ | 理由 |
|---|---|---|---|
| 1 | 服务端 `quack.db` 保持唯一权威库，安卓通过 WS/HTTP 读写 | ✅ **推荐** | 与桌面端完全同构；零数据库改造；所有一致性机制已经跑通 |
| 2 | App 内嵌/直连服务端那个 `quack.db` 文件 | ❌ 不可行 | 见下方三条硬理由 |
| 3 | 两端各存一份，定时/手动同步 | ❌ 别做 | 等于重造一套双向同步协议：离线冲突、消息 id 冲突、seq 空洞全要自己处理，而第 1 种方案已经解决了这些问题 |

**为什么"直连 SQLite 文件"不可行：**

1. **SQLite 不是网络数据库**。它设计前提是"单个文件系统、单机进程内并发"。走 SMB / 网络共享让两台设备同时写，会踩到文件锁语义不一致，轻则 `SQLITE_BUSY`，重则**库损坏**（官方明确不建议把 SQLite 放在网络文件系统上）。
2. **等于把整库交给任何人**。APK 是可以反编译的；一旦 App 里有打开 `quack.db` 的能力，任何拿到安装包的人就拿到了**全部账号的密码哈希、全部聊天记录、全部好友关系**。这不是"权限没做好"，是架构性泄露。
3. **服务端的数据本来就不在文件里现成躺着**。元数据是内存态定时快照写的（`PersistenceService` 每 2 秒算指纹、有变化才重写），客户端读文件会读到**事务中间态/落后状态**，而且 `-wal` 里还有未 checkpoint 的数据。绕过服务端读写，等于绕过了所有业务校验（谁有权看哪个会话、未读怎么算、seq 怎么分配）。

> 顺带说明：如果将来要换成 MySQL，也是**只动服务端**（`sql/schema.sql` 已经写好 MySQL DDL，把 `UserService/FriendService/MessageStore` 换成 Mapper 即可，见 `architecture.md` §3）。安卓端一行都不用改——这本身就是"数据库不该出现在客户端"的最好证明。

## 3. 所以"数据互通"是免费的：四条现成机制

安卓端只要**老老实实当一个客户端**，下面这些场景开箱即用：

| 场景 | 靠什么现成机制 |
|---|---|
| 手机发消息，电脑立刻看到 | 服务端投递 + `PushService.deliver` 对所有设备扇出 |
| 电脑上读过的消息，手机未读角标消失 | `msg.read` → `unread.push` 推给同账号其它设备 |
| 手机关机两天，开机补收 | 设备级游标 + 登录时 `catchUp` 补发 100 条/会话，不够下次继续 |
| 手机里翻聊天记录最上面一页 | `sync.req{sinceSeq}` / `history.req{beforeTs}` |
| 换手机、重装 App | 新 deviceId 游标为 0，登录后拿全量最近历史 |
| 改了备注/头像/资料 | `friend.remark.push` / `friend.updated` 定向推给好友 |
| 消息不重、不乱序 | `clientMsgId` 幂等 + 会话内 `seq` + 客户端按 id/seq 去重 |

**没有一条需要改数据库。** 需要动手的只有三件事：手机上的登录页（填服务器地址）、一套 Android 的 WS/HTTP 实现、一个和桌面端不同的 `deviceId`。

## 4. 真正难的地方（分项打分，5 = 最难）

| 分项 | 难度 | 为什么 |
|---|---|---|
| 数据互通 / 数据库 | **1** | 服务端已是唯一数据源 + 多设备模型；零改造 |
| 协议移植 | **2** | JSON + 109 个命令字，无二进制、无加密握手；OkHttp WebSocket 一百多行可跑通登录收发 |
| UI 重写 | **4** | 桌面 9,645 行 JavaFX + 1,440 行 CSS **全部不可复用**；范式要从"多列并排 + 无边框窗口 + 右键菜单"改成"单列导航 + 底部 Tab + 全屏页 + 长按菜单" |
| 媒体与系统集成 | **4** | 相册/相机/文件选择、图片压缩与 EXIF、视频封面与播放、300MB 移动网络上传、下载与权限、通知渠道 |
| 语音通话 | **5** | 见 4.3，协议本身就有物理上限 |
| 通知与后台存活 | **5** | 见 4.1，这是唯一需要**新增服务端能力**的地方 |

### 4.1 最硬的一关：手机上的长连接活不下来

桌面端的模型是"进程常驻 + 25s 心跳"。Android 上这套会失效：

- Doze / App Standby / 厂商省电策略（小米/华为/OPPO/vivo 尤其激进）会冻结甚至杀掉后台进程；
- 现在的协议**没有"唤醒"能力**：用户离线时服务端什么都不存（游标机制只在登录时补），所以 **App 没在前台 = 收不到任何通知**。产品上这是致命的——用户不会主动打开一个不会响的聊天软件。
- 必须新增的能力：前台服务 + 常驻通知（能跑通，但耗电、且被 OEM 限制）、或接入推送通道。国内没有 FCM，现实选项是小米/华为/OPPO/vivo 推送 SDK，或极光/个推这类聚合推送，或自建（ntfy/自建 WS 长连 + 短信兜底）。

**这条的工程量不在 App 里，在服务端加一条推送通道**，但它决定了"能不能当日常 IM 用"。

### 4.2 UI 重写是工作量主体

`AppContext.java` 单文件 1,799 行，承载了重连退避、去重、回执、同步、会话状态、媒体、通话的全部编排；`ChatPane` 38KB、`MomentSpaceView` 40KB、`GroupInfoView` 31KB、`MessageCell` 28KB。
安卓端要重写等价的状态编排（建议拆成 Repository + ViewModel，别照搬这个"上帝对象"），再加 40 多个界面。**预计 8,000–12,000 行 Kotlin/Compose。**

### 4.3 语音通话：协议本身有物理上限

现在是 **base64 PCM 走 JSON 文本帧**：16kHz/16bit/单声道，20ms = 640 字节 → base64 后约 856 字节 + JSON 信封，50 帧/秒 ≈ **45KB/s 上行**，双向接近 90KB/s；没有抖动缓冲、没有回声消除、服务端不混音（`README` 自己写了"局域网级"）。

- 桌面端在局域网能用；手机上用 4G/弱网会明显断续、耗电、噪音。
- 安卓侧要做：`AudioRecord`/`AudioTrack`、录音权限、音频焦点、蓝牙耳机路由、通话中前台服务。
- **建议顺带升级协议**：`call.audio` 改成二进制帧 + Opus 编码（体积降一个数量级），或直接换 WebRTC。这属于协议演进，会同时改桌面端。

### 4.4 安卓的安全红线（必须提前处理）

- **Android 9+ 默认禁止明文 HTTP**（`cleartextTrafficPermitted=false`）。所以要么上 `wss://` + 正式证书（`application-tls.yml` 可用，但需要域名），要么只在调试包放行明文（`network_security_config.xml`）。**这是"上线"和"局域网自测"的分界线。**
- 密码不能像桌面那样"记住上次账号"就算了；要用 `EncryptedSharedPreferences`/Keystore。好在现有服务端已经发了 7 天 token，**建议加一条 `login.token` 命令**，让冷启动不用重输密码（现在 token 只给 HTTP 上传用）。
- 服务端 `RateLimiter` 是**按 IP** 限流（登录失败 10 次/5 分钟/IP）。移动网络是运营商级 NAT，大量用户共享出口 IP，这个策略在手机端会**误伤**——需要改成按账号/设备为主、IP 为辅。

### 4.5 其他小坑（都会真实遇到）

- 自签证书在 Android 上默认不被信任（要么正式证书，要么给 App 内置 trust anchor，别用"忽略证书校验"糊过去）；
- 切换 WiFi ↔ 4G 会断连，要快速重连 + `sync.req` 补洞（协议已支持，客户端要做）；
- 心跳与 Doze：25s 心跳在后台会被吞，前台服务要单独处理；
- 刘海/手势区/字体缩放/深色模式/无障碍/多机型适配；
- 文件 300MB 在移动网络下需要断点续传或分片（现有接口是单次流式，没有 Range 上传）。

## 5. 三条路线

| 路线 | 做法 | 工期（单人全职） | 评价 |
|---|---|---|---|
| **A. 原生 Kotlin + Compose**（推荐） | 只写客户端；服务端加 `login.token` 和推送通道 | MVP 3 周 / 日常可用 10–14 周 | 唯一能做出"像 App"的体验；协议、文件接口、多端机制全复用 |
| **B. Web 客户端 + 套壳（PWA/TWA）** | 用同一协议写一份 Web UI，再打包成 App | 3–5 周 | 最省力，一套代码覆盖手机+浏览器；代价是通话、后台通知、文件选择、键盘体验打折，且需要服务端支持 `Origin`（已放行 `*`） |
| C. 把桌面端塞进手机（Termux/远程桌面） | — | — | JavaFX 没有 Android 版本，不成立 |
| D. 复用 Flutter 一次写两端 | — | — | **不推荐**：上一轮已经试过，结论是"又卡又丑"并删掉了。难点从来不是语言，而是手机上的信息密度与交互范式——换框架不会自动解决 |

> 如果目标只是"想在手机上用"，选 B；如果想做一个能上架的安卓 App，选 A。

## 6. 如果做 A：分阶段计划

| 阶段 | 内容 | 工期 |
|---|---|---|
| **P0 打通** | 服务端 `wss` 部署 + 冻结协议（Cmd/DTO 生成 Kotlin 模型）+ 手机热点下用 `websocat` 手工发 `login` 验证可达 | 2–3 天 |
| **P1 聊天核心** | Kotlin + OkHttp + Room：登录/注册/心跳/重连、会话列表、私聊文本、`sync.req` 历史、已读未读、图片（Photo Picker + 压缩 + 上传） | 2 周 |
| **P2 关系链** | 好友搜索/申请/审批/备注、资料页、群聊与群管理（成员、公告、审批、精华、踢人、转让） | 2–3 周 |
| **P3 空间与文件** | QC 空间（9 图/视频/评论/点赞/转发）、文件消息（下载/打开/Range）、视频播放（ExoPlayer） | 2–3 周 |
| **P4 通话** | 信令 + `AudioRecord/AudioTrack` + 音频焦点 + 前台服务（建议同时把 `call.audio` 换 Opus 二进制帧） | 1–2 周 |
| **P5 通知与打磨** | 前台服务保活、通知渠道、厂商推送、深色模式、字体缩放、无障碍、多机型 | 2–4 周 |

**服务端改动清单：**

- 必须：`wss` 证书部署；`deviceId` 约定（如 `android-<uuid>`）；DTO 契约冻结。
- 建议：`login.token` 命令；离线推送通道；`call.audio` 二进制/Opus；上传断点续传；限流改为"账号优先、IP 兜底"。

## 7. 验收标准（"数据互通"的 Definition of Done）

1. 同一 QC 号，桌面端 + 安卓端**同时在线**，互不踢线（同一 `deviceId` 才互踢）。
2. 手机发文本，桌面 1 秒内出现；桌面发图片，手机能直接看到缩略图。
3. 桌面读完一个会话，手机的未读角标同步清零（`unread.push`）。
4. 手机关机 24h 再登录，历史消息按游标补齐，无重复、无空洞。
5. 手机改昵称/头像，桌面好友列表和聊天头部同步更新。
6. 手机重装（新 deviceId）后登录，能拉到最近历史，且不影响桌面端的游标。
7. 手机在 4G 下切 WiFi 不断线（或断线自动重连 + 补洞）。
8. 服务端重启一次，客户端能自动重连并补上重启期间的消息（现在服务端内存态 + SQLite 快照，消息不丢）。

## 9. 一句话回答

**不难，但也不是"加个壳"那么简单。**
"共用同一套数据库、数据互通"这件事，你的架构**已经做完了**——服务端就是唯一数据源，多设备、游标、补发、多端同步都是现成的，安卓端只要接同一套 JSON 协议就能互通。
真正要付出的，是**再写一个 1 万行级别的客户端 UI**，外加**服务端补一条手机能收到的推送通道**。前者是体力活，后者是唯一的技术缺口。
